# 数据根重定向的生效边界：轻任务子进程跟随，主会话进程暂留 home

**Status**: accepted（2026-11-13，含当日真实迁移复核）

桌面客户端支持把数据目录重定向到自定义位置（`setting.json` 的 `dataBaseDir`）。命令行运行时（CLI）解析数据根只认环境变量 `ZCODE_DATA_BASE_DIR`，未注入时回退用户主目录，并不读取该设置。插件自身读配置的路径助手是跟随重定向的，于是出现同一条渠道定义"插件读得到、子进程读不到"的分叉：润色/标题等轻任务起的独立进程拿不到重定向后的个人渠道配置。

迁移的覆盖面比设置项字面更窄（2026-11-13 实机复核，迁移前后基线对照）：

- **会话数据（`cli/`）不随 `dataBaseDir` 迁移**。迁移只把 `v2` 复制到新数据根，home 原件保留；桌面端自己的 CLI 进程也继续写 home 的 `cli/db`——迁移后桌面端新建会话的 session 行仍落 home。因此**会话列表本身不会因迁移分叉**（此前"迁移后没问题"的经验成立）。
- **会分叉的是 `v2/tasks-index.sqlite`**（置顶/未读/归档与侧栏任务索引）。桌面端读写重定向副本，插件直读硬编码的 home 副本：实测桌面端新建 3 条会话的任务行只出现在重定向副本，插件新建会话的任务行两边都没有（CLI 进程本身不写任务索引）。两端各自置顶/归档互不可见，属于真实存在的分叉面。
- **跨端会话可见性不受影响**：桌面端侧栏同样合并 CLI 会话列表（2026-11-13 截图实测：桌面端能看到插件新建的会话，插件能看到桌面端新建的会话）；任务行缺失只影响元数据与过滤，不导致会话消失。
- 桌面端**没有**把 `dataBaseDir` 传给自己的 CLI 进程；插件若把主 app-server 单点改为跟随重定向，CLI 会在重定向目录新建一份空的 `cli` 库，这才制造真正的会话分叉。所以"主会话进程暂留 home"不是保守，而是与桌面端行为对齐。

**Decision**

- 数据根只下发给与会话库无关的轻任务子进程：润色/标题的 `generateText` 专用 app-server，以及一次性 CLI 调用。
- 主 app-server 与 CLI `--resume` 通道保持 home 数据根（与桌面端 CLI 行为一致；会话数据不随重定向迁移）。
- 内置渠道目录的定位（runtime 缓存候选）跟随数据根；安装副本与 AppData 兜底候选次序不变（含历史误拼位置兼容）。
- 后续待办（已实施，2026-11-13）：插件直读的 `v2` 面（`tasks-index.sqlite`）跟随 `dataBaseDir`，与桌面端同一份任务索引（重定向文件缺失回退 home）；`cli` 会话数据保持 home。

**Considered Options**

- 全量跟随（所有子进程与所有直读路径统一到重定向数据根）：会连 `cli` 一起重定向，制造会话库分叉（桌面端自己都不这么做），且涉及迁移期双源读取，风险与工作量远超本次缺陷。
- 只给一次性 CLI 调用注入：实现最小，但 `generateText` 快速通道仍失效（先降级再可用），润色延迟与失败面仍在。

**Consequences**

- 重定向用户的润色/标题恢复可用，且与桌面端看到同一份渠道定义。
- 任务索引跟随 `dataBaseDir` 后，两端的置顶/归档/未读读写同一份：桌面端归档的会话在插件列表同步隐藏，反之亦然。插件新建、客户端尚未索引的会话在置顶/归档时由插件 UPSERT 补行。
- 切换数据根后需重启 IDE，任务索引路径才重新解析（路径在 client 构造时确定；与桌面端切目录需重启一致）。
- 真机验收（2026-11-13，PyCharm + 真实迁移）：自定义渠道润色走 generateText 成功（专用 app-server 收到 `dataBaseDir`），任务索引的归档隐藏与置顶两端同步。
- 不再把"会话库分叉"当作文档事实：`cli` 不迁移是客户端既定行为，会话列表与删除所依赖的会话库始终同源。
